The work

Analysis

You run a supplied, staged Python workflow from the command line. There is no notebook. Each stage refuses to run until its prerequisite is met, and says why in one sentence. That makes the fair-comparison rules {{help five-rules}} part of the workflow, not a promise.

The protocol

Each dataset is split once, before anything else: 80% development {{help development-set}} and 20% test {{help test-set}}, stratified. The development rows are split again into 5 fixed folds {{help fold}}. Every model uses the same folds.

  1. Commit Before results in DECISIONS.md {{help decisions-md}}.
  2. train fits every model on the supplied folds and writes development out-of-fold (OOF) {{help oof}} probabilities, plus training and CV AUROC per fold.
  3. explore shows, for diabetes, each model's threshold under the job's rule {{help diabetes-rule}}, using development data only.
  4. Commit Before test: your diabetes model and the reason.
  5. test refits on all development rows and predicts the locked test rows once.
  6. Fill in Verification and Recommendations, then export them for your app.

The files the workflow exports

Your app reads only these files {{help results-files}}. Commit and push results/ so your hosted app can load them. Every probability is rounded to 4 decimals before any metric is computed, so m11 recomputes the exported numbers exactly.

FileWritten byHolds
results/<key>_dev.jsontrainrow_id, fold and y (the label) of every development row; commit (your Before results commit); and for each model, oof (one out-of-fold probability per row) and folds (per fold: train_auroc, cv_auroc, row counts). The starter's files hold the baseline only.
results/<key>_test.jsontestrow_id and y of every test row, and for each model, p (one test probability per row) and auroc.
results/test_record.jsontestYour Before test choice and reason, your Before test commit, the saved diabetes threshold with its rule and its development and test counts, and a log of every test run.
results/decisions.jsonexportYour parsed DECISIONS.md answers, which sections are complete, your word count, and recommendations (the three lines your app shows at the top).
Example: read your results in Python 
import m11

dev = m11.load("diabetes_dev")
p, y = m11.oof(dev, "logreg")                 # development out-of-fold
c = m11.confusion(p, y, 0.5)                  # {"tp", "fn", "fp", "tn"}
print(m11.metrics(c)["sensitivity"])          # None means undefined
print(m11.threshold_for_rule(p, y)["threshold"])
print(m11.fold_summary(dev)["favoured"])
Example: read your results in the browser (Route A) 
import * as m11 from "./m11.js";

const dev = await m11.load("diabetes_dev");
const [p, y] = m11.oof(dev, "logreg");
const c = m11.confusion(p, y, 0.5);
console.log(m11.metrics(c).sensitivity);      // null means undefined
console.log(m11.foldSummary(dev).favoured);

What check.py verifies

  • The data files match their fingerprints in data/manifest.json.
  • Development and test rows are disjoint, and every development row has exactly one out-of-fold prediction from the supplied folds.
  • knn and svm are Pipeline objects, with scaling inside.
  • No outcome or ID column is used as a predictor.
  • The default logreg CV AUROC matches the reference within ±0.005.
  • Recomputed metrics match the exports, and confusion counts add up.
  • The saved diabetes threshold matches the rule for your chosen model.
  • Test predictions cover test rows only, and test_record.json matches Before test.
  • In git history, Before results was committed before the first results commit, and Before test before the test results.

Every failure says what to fix in one sentence. Fix the first one, then run it again.
